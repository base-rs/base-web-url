# URL Syntax and Resolution

## Requirement

URLs with a scheme and URL references that may be relative must be distinct types: `Url` always has a scheme, `UrlReference` may not, and every `Url` converts into a `UrlReference`. Paths are a separate `UrlPath` type, and authorities a separate `Authority` type.

Parsing must follow the generic syntax of RFC 3986 exactly. A character outside the grammar of its component, a `%` not followed by two hexadecimal digits, an invalid scheme, user information, or host, a port that is not a number from 0 to 65535, and a path that cannot follow the other components are errors. Components are kept percent-encoded as written, except that the case-insensitive scheme is stored in lowercase; a query or fragment that is present but empty is kept distinct from an absent one, so writing a parsed reference reproduces its input apart from the scheme's case.

Reference resolution against a base with a scheme must follow RFC 3986 section 5.2 exactly, including its examples in section 5.4 and its removal of dot segments from paths without a leading `/`, and must keep empty path segments. Where the RFC's algorithm would produce a path that reads differently when written, a path beginning with `//` without an authority or a relative reference whose first segment contains `:`, the result gains a leading `/.` or `./`. Resolution between relative references and paths, which the RFC does not define, removes dot segments in the same way, except that a relative result keeps the leading `..` segments it cannot resolve, and names a directory it reduces to as `./` rather than the empty reference, which means the current document. This is RFC 3986, not the WHATWG URL Standard that browsers follow. Appending to a path as a directory is a separate operation, `join`, and collapsing repeated separators or treating percent-encoded dots as dot segments happens only through the explicit, lossy `simplify`.

Building a path from decoded values, with `from_components` or `join_component`, must encode each value as exactly one segment, so a `/` within a value never becomes a separator, and must reject a value of `.` or `..`, which a URL cannot express as data; `join_component` also rejects an empty value. A value appended this way can never navigate. `resolve` and `join` combine URL syntax and do not confine their result to the base, and their documentation must say so.

`resolve` and `join` treat a percent-encoded dot as data, as RFC 3986 does; the operations about what a path names, `file_name`, `directory`, `parent`, `simplify`, and `to_local_path`, treat it as a dot, as servers that decode it do, and `file_name` is absent for a final dot segment, so a decoded name is never `..`.

A path ending with `/` names a directory, and any other path names a file within its directory. `directory` must return the directory containing the resource a path names, and `parent` the directory one level above it, both in directory form and after resolving dot segments, including percent-encoded ones, so that neither is deeper than the path and resolving a reference without a leading `/` or `..` against either stays within it. Empty segments count as levels, as they do in resolution. `parent` must return `None` at the root and at the top of a relative path, where what lies above depends on the base. `relative_to` must never return an absolute or network-path reference, and resolving its result against the base must give the target with dot segments removed. Form content, including `application/x-www-form-urlencoded` queries, belongs to `base-web-content`.

The crate must have no dependencies, and must not depend on an HTTP or web framework crate.

## Rationale

The user chose separate types, mirroring `base-web-media-type`'s `MediaType` and `MediaRange`, so that a missing scheme is a type error rather than a runtime check. The user chose RFC 3986 exactly, both for parsing and for resolution, over the Ruby `protocol-url` gem's more permissive parser and its resolution, which collapses repeated slashes; the gem's directory-style joining, its `pop: false` option, is kept as `join` because the user relies on it. Keeping segments encoded and building paths from components preserves the gem's careful separation of URL syntax from decoded values. The user asked that path semantics be safe and meaningful, noting that a parent can mean different things in different contexts, so the two meanings are separate operations with one definition each, rather than the gem's lexical `parent`, which can name the same directory or a deeper one; and the review that preceded the first release found that the gem's `relative` could produce a network-path reference and that `..` passed as a value navigated. The user agreed that all form encoding, flat and nested, belongs to `base-web-content`, and the dependency rule follows the `base-web-*` family rule in `base-project`'s Package Organization guide.

## Scope

The `base-web-url` crate's `Url`, `UrlReference`, `UrlPath`, `Authority`, `UrlError`, `encode_component`, and `decode_component`, and their parsing, writing, comparison, resolution, and joining.

## Validation

The integration tests under `tests/` check accepted and rejected input for each component, round trips, every resolution example of RFC 3986 section 5.4, the adjustments for ambiguous results, segment-preserving construction and its rejection of dot values, and the directory and parent of files, directories, dot segments, empty segments, and relative paths. Property tests compare resolution with a literal transcription of RFC 3986 section 5.2 for bases with and without an authority and a leading `/`, check that `relative_to` round-trips and never returns an absolute path, and that ancestors terminate within their directory. Inspect `cargo tree -p base-web-url -e normal`, which must list no dependencies.
